# 发布与运维手册（Stage 7）

## 1. 单机边界与容量

- 首版只允许本机 Docker Compose；Nginx `127.0.0.1:8080` 是唯一业务入口。
- MinIO 固定 `minio/minio:RELEASE.2025-09-07T16-13-09Z`；健康检查必须用镜像自带的
  `mc ready local`。该镜像不含 `curl`/`wget`，用它们探测会让 `minio` 永远 unhealthy，
  进而卡住 `minio-init`、API 与 Nginx。
- Geo Worker 默认并发 2。提升前必须同时观察临时盘、内存、CPU、PostgreSQL 与 MinIO I/O。
- 单文件目标为 2–100 GB；临时盘至少按最大源文件 2–3 倍规划。默认预检倍率为 2。
- 例行夹具验证不等同于 100 GB 压测。未在目标硬件实测前，不承诺固定吞吐或完成时间。
- 首版支持 GeoTIFF/BigTIFF、GeoJSON、打包 Shapefile、GeoPackage 与普通附件；不支持完整
  STAC API、Excel/CSV 导出、SSE/WebSocket、仓库中不存在的遥感算法和多机高可用。

## 2. 从源码构建发布候选

```bash
cp .env.example .env
docker compose build
docker compose up -d
docker compose ps
curl -fsS http://localhost:8080/api/v1/readyz
env UV_CACHE_DIR=/tmp/remote-scene-uv-cache uv run python scripts/verify_release.py
```

API 启动命令自动执行 `alembic upgrade head`。发布候选必须只依赖源码、镜像构建文件与
Alembic，不得手工编辑数据库。迁移链检查：

```bash
uv run alembic heads
uv run alembic history
uv run alembic upgrade head
```

## 3. 备份与恢复

为获得 PostgreSQL 与 MinIO 的一致备份，先停止所有会产生写入的应用进程，再分别备份。

```bash
docker compose stop nginx api worker dispatcher scheduler recovery cleanup
docker compose exec -T db pg_dump -U app -d remote_scene -Fc > remote_scene.dump
# 宿主机预先安装 mc，并把备份目录替换为受保护的实际路径
mc alias set remote-scene-local http://127.0.0.1:9000 minioadmin minioadmin
mc mirror remote-scene-local/remote-scene /实际备份目录/remote-scene
docker compose start api worker dispatcher scheduler recovery cleanup nginx
```

示例口令必须替换为 `.env` 中的实际值，备份目录不得位于 Compose 数据卷内。恢复时使用
同版本空栈：先 `pg_restore --clean --if-exists` 恢复数据库，再用
`mc mirror` 恢复对象，最后执行 `alembic upgrade head` 并启动应用。恢复演练必须核对：

- `readyz` 全部组件为 `ok`；
- `object_blob.reference_count` 与版本引用一致；
- READY 栅格的 COG/缩略图存在并可通过受控瓦片 URL 读取；
- Outbox 积压能继续投递，RUNNING 租约过期后由 recovery 回收。

## 4. 生命周期与故障恢复

`DELETE /api/v1/assets/{id}` 立即隐藏资产，并记录 `deleted_at/purge_after`。默认 7 天内可用
`POST /api/v1/assets/{id}/restore` 恢复。到期后独立 cleanup 进程物理删除数据库资产，并把
MinIO 删除写入 `object_cleanup_task`；删除失败指数退避。共享 blob 只有真实 live 引用为零
才会删除。监测输入快照仍引用的版本不会被物理清理。

Worker 每个任务使用独立目录，步骤边界检查取消请求；软时限负责落库诊断，硬时限负责
终止失控子进程。进程崩溃后由 Job 租约与 recovery 重投，任务重试仍受 `max_attempts` 限制。

## 5. 指标与排障

Prometheus 位于 `127.0.0.1:9090`。可选面板：

```bash
docker compose --profile observability up -d grafana
```

Grafana 位于 `127.0.0.1:3000`，自动加载 `Remote Scene / Remote Scene Operations`。关键指标：

- `remote_scene_outbox_backlog`、`remote_scene_rabbitmq_queue_depth`；
- `remote_scene_jobs{status=...}`、`remote_scene_job_failures_24h`；
- `remote_scene_job_duration_seconds`、`remote_scene_worker_utilization_ratio`；
- `remote_scene_storage_bytes`、`remote_scene_cleanup_backlog`；
- `remote_scene_operational_collector_up`。

常见诊断顺序：

1. `readyz` 定位 DB/MinIO/RabbitMQ/TiTiler；
2. 用 API problem 中的 `trace_id` 检索结构化日志；
3. 查询 Job 事件与 `last_error`，区分确定性失败、`NEEDS_INPUT`、瞬时重试和租约丢失；
4. Outbox 增长先查 RabbitMQ，队列增长再查消费者与临时盘；
5. cleanup 增长时检查 `object_cleanup_task.last_error` 和 MinIO 权限；
6. `TEMP_STORAGE_INSUFFICIENT` 必须扩容临时盘或降低并发，不应盲目重试同一版本。

## 6. 发布前测试与夹具

例行门禁使用仓库内固定夹具；夹具的 CRS、波段、几何与预期结果见
`doc/验收基线与测试夹具.md` 和 `tests/fixtures/README.md`。

```bash
uv sync --all-groups
uv run pytest -m "not integration"
uv run ruff check .
uv run pyright
uv run python scripts/verify_release.py
```

真实基础设施集成测试必须显式提供隔离环境，不能以 Mock 结果替代：

```bash
export APP_INTEGRATION_DATABASE_URL='postgresql+psycopg://app:app@127.0.0.1:5432/remote_scene'
export APP_INTEGRATION_RABBITMQ_URL='amqp://app:app@127.0.0.1:5672/'
export APP_INTEGRATION_MINIO_ENDPOINT='127.0.0.1:9000'
export APP_INTEGRATION_MINIO_ACCESS_KEY='minioadmin'
export APP_INTEGRATION_MINIO_SECRET_KEY='替换为实际口令'
export APP_INTEGRATION_MINIO_BUCKET='remote-scene'
uv run pytest -m integration
```

最后在全新 Compose 数据卷上逐项执行 A1–A6；只有可观察结果全部符合验收基线，才可把
Stage 6 和 Stage 7 标记为“已完成”。
