# Python 遥感后端阶段迁移实施方案

> 状态：当前实施进度以 `README.md` 阶段表为唯一看板；本文只维护阶段门禁与退出条件。
>
> 依据：《总体架构》及既有 Java 业务代码盘点
>
> 存放位置：本文档现位于 Python 实现仓库 `remote-scene-platform/doc/`。Java 参考仓库只读核对旧业务行为。

## Problem Statement

当前后端基于若依单体工程，遥感业务与若依的用户、菜单、权限、监控、代码生成、Quartz、通用返回结构和本地文件系统深度混合。业务接口存在重复模型、重复入口和历史实现缺陷，包括：

- “上传数据”和“卫星数据”字段高度重复，但使用两套表和两套 CRUD。
- `SendTask` 与矿山卫星任务新增执行相同的空间匹配和任务保存逻辑。
- 大文件分片、合并、GDAL 转换和缩略图生成阻塞在 HTTP 请求中。
- 文件存储依赖本机路径，返回值中混入自定义字符串分隔协议。
- MySQL 保存业务数据、PostgreSQL 保存空间数据，业务事务跨库割裂。
- 任务中的资产关联以逗号分隔 ID 保存，无法形成可靠外键和执行快照。
- 现有周期字段没有真正的调度执行能力。
- API 响应、分页、错误处理和鉴权依赖若依约定，无法作为新前端和计算平台的稳定边界。

项目目前只有代码仓库，没有需要保留的生产业务数据。因此迁移重点不是数据库原样搬运，也不是 Java 到 Python 的机械翻译，而是完整保留有效业务用例，在 PostgreSQL/PostGIS、MinIO、RabbitMQ、Celery 和 TiTiler 上重建可扩展的资产与任务平台。

## Solution

在独立新仓库中建设 Python 3.12 模块化单体。代码按业务域垂直切分，运行时拆为 FastAPI API、Outbox Dispatcher、独立 Scheduler、Celery Geo Worker 和 TiTiler 等进程。

迁移采用“纵向闭环优先”的阶段策略：先交付一条可人工验收的栅格上传到地图展示链路，再扩展矢量、附件、目录、生态参数和监测计划。每个阶段都有明确依赖、工作包、人工端到端验收场景和退出条件；上一阶段未满足退出条件时，不进入依赖它的下一阶段。

业务迁移以用例为单位：旧 Controller 只作为业务规则来源。新系统统一资产模型、不可变版本、成果对象、Job 状态机和 Outbox 可靠投递，主动修复旧路由、重复逻辑、逗号 ID、同步大文件处理和本地路径等历史问题。

首版不实现鉴权，只在本地开发机运行。所有需要属主信息的业务表预留 nullable 的 `owner_id` 和 `created_by`，Service 使用统一 `ActorContext`，首版固定为匿名系统操作者，为后续 JWT 与 `ADMIN/USER` 权限接入保留稳定接缝。

## User Stories

1. As a backend developer, I want to start all required services with one Docker Compose command, so that I can reproduce the development environment on Windows Docker Desktop/WSL2.
2. As a backend developer, I want database migrations to create PostgreSQL and PostGIS structures deterministically, so that schema changes are reviewable and repeatable.
3. As a frontend developer, I want every business API to live under `/api/v1`, so that the new frontend has a stable versioned integration boundary.
4. As a frontend developer, I want HTTP status codes and RFC 9457 errors, so that I can handle validation, conflicts and dependency failures consistently.
5. As a frontend developer, I want list APIs to return `items`, `total`, `page` and `page_size`, so that pagination behavior is uniform across modules.
6. As a data manager, I want to create a multipart upload session, so that large remote-sensing files do not pass through the FastAPI process.
7. As a data manager, I want to upload parts directly to MinIO with presigned URLs, so that files between 2 GB and 100 GB can be uploaded reliably.
8. As a data manager, I want an interrupted multipart upload to be resumed, so that already uploaded parts do not need to be retransmitted.
9. As a data manager, I want upload completion to create an immutable asset version and processing Job, so that every uploaded file is traceable.
10. As a data manager, I want duplicate binary files to reuse the same immutable object, so that MinIO storage is not wasted.
11. As a data manager, I want two logical assets to reference the same binary object when their business metadata differs, so that physical deduplication does not collapse business records.
12. As a remote-sensing analyst, I want a GeoTIFF to be validated and converted to COG automatically, so that it is suitable for cloud-native map access.
13. As a remote-sensing analyst, I want the COG to preserve the source CRS, so that ingestion does not introduce avoidable reprojection loss.
14. As a frontend developer, I want every spatial asset to expose an EPSG:4326 footprint, so that it can be searched and drawn consistently on the map.
15. As a remote-sensing analyst, I want default RGB or grayscale rendering to be inferred from band metadata, so that most rasters can be previewed without manual configuration.
16. As a remote-sensing analyst, I want missing CRS or ambiguous band metadata to pause processing in `NEEDS_INPUT`, so that the system does not silently create spatially incorrect data.
17. As a remote-sensing analyst, I want to provide missing metadata and resume from the interrupted step, so that I do not need to re-upload a large source file.
18. As a frontend developer, I want a short-lived tile URL for a ready raster version, so that the map can use TiTiler without exposing MinIO or TiTiler directly.
19. As a data manager, I want GeoJSON, Shapefile and GeoPackage inputs to retain their original files and import their features to PostGIS, so that they support both download and feature-level spatial queries.
20. As a data manager, I want vector feature properties stored flexibly while geometries remain spatially indexed, so that heterogeneous source schemas do not require a table per uploaded file.
21. As a data manager, I want ordinary attachments to be managed as assets without spatial processing, so that supporting documents share versioning, storage and lifecycle behavior.
22. As a data manager, I want a logical asset to have multiple immutable versions, so that newer files do not overwrite evidence used by previous Jobs.
23. As a remote-sensing analyst, I want Jobs and monitoring runs to reference concrete asset versions, so that historical outputs remain reproducible.
24. As a data manager, I want core searchable metadata in typed columns and optional metadata in JSONB, so that queries remain efficient while business templates can evolve.
25. As a data manager, I want JSON Schema validation for type-specific metadata, so that flexible JSONB properties still have enforceable contracts.
26. As a data manager, I want to manage a hierarchical data-resource catalog, so that assets can be organized by stable business categories.
27. As a data manager, I want to manage satellite and sensor catalogs, so that raster assets can reference normalized acquisition sources.
28. As an ecological analyst, I want to manage ecological parameters and their mappings to resource categories, so that monitoring plans can select suitable input data.
29. As a user, I want asset search to filter by type, status, time, catalog, satellite, sensor and spatial geometry, so that I can find relevant data without separate legacy queries.
30. As a user, I want spatial request geometries to use EPSG:4326 GeoJSON Polygon or MultiPolygon, so that API and frontend map coordinates have one documented convention.
31. As a monitoring planner, I want to create plans with a mine boundary, ecological parameters, resource constraints and a recurrence rule, so that recurring monitoring can be described explicitly.
32. As a monitoring planner, I want simple intervals and RFC 5545 RRULE schedules, so that both common and calendar-based recurrence can be represented.
33. As a monitoring planner, I want each run to select only matching assets added since the previous successful run, so that the same data is not repeatedly processed.
34. As a monitoring planner, I want every run to preserve an immutable input snapshot, so that I can explain exactly which asset versions were selected.
35. As an operator, I want the scheduler to catch up only the most recent missed occurrence after downtime, so that startup does not create a task storm.
36. As an operator, I want PostgreSQL to be the source of truth for Job state, so that RabbitMQ delivery state does not replace business state.
37. As an operator, I want Job creation and Outbox creation in one database transaction, so that a committed Job cannot silently lose its dispatch message.
38. As an operator, I want workers to retry transient failures but stop on deterministic data errors, so that retries are useful rather than wasteful.
39. As an operator, I want every processing step to be idempotent, so that redelivery or retry does not duplicate artifacts or corrupt state.
40. As a frontend developer, I want to poll a Job resource for progress and diagnostics, so that the first version does not require long-lived connections.
41. As a future frontend developer, I want Job state changes recorded as events, so that SSE can be added later without replacing the Job model.
42. As a data manager, I want deletion to hide an asset immediately but retain it for seven days, so that accidental deletion can be recovered.
43. As an operator, I want expired deleted assets and unreferenced objects cleaned asynchronously, so that cross-system deletion failures can be retried safely.
44. As an operator, I want structured JSON logs and a trace identifier to follow an API request through a Job, so that failures can be diagnosed across processes.
45. As an operator, I want Prometheus metrics for APIs, queues, workers, Jobs and storage, so that bottlenecks and failures are visible.
46. As a maintainer, I want an explicit legacy-to-new use-case matrix, so that every old business endpoint is either migrated, merged, replaced or intentionally excluded.
47. As a maintainer, I want the new model to align with core STAC concepts, so that STAC-compatible APIs can be added later without restructuring assets.
48. As a maintainer, I want API and Geo Worker dependency groups separated, so that the API image remains small and scientific dependencies can evolve independently.
49. As a maintainer, I want manual end-to-end acceptance scenarios backed by small deterministic geospatial fixtures, so that the migrated system can be validated as a whole.
50. As a maintainer, I want a small set of integration tests only at high-risk infrastructure seams, so that the suite catches real regressions without a large unit-test suite.
51. As a future administrator, I want owner and actor seams already present, so that JWT and `ADMIN/USER` authorization can be added without redesigning every business service.

## Implementation Decisions

### 1. Migration principles

- Preserve business capabilities and externally observable outcomes, not Java class structure or existing URL compatibility.
- The new frontend will integrate with new APIs; legacy request paths, `AjaxResult`, `TableDataInfo`, permission annotations and generated CRUD conventions are not compatibility requirements.
- No production data migration is required. Repository SQL is used only to understand legacy structure; useful reference values, if discovered, become explicit seed data.
- The Python implementation lives in this repository. The legacy Java repository remains a read-only behavioral reference; migration specifications live in `doc/`.
- A legacy business endpoint is not considered handled until the use-case matrix records one of: `MIGRATED`, `MERGED`, `REPLACED`, or `EXCLUDED_WITH_REASON`.

### 2. Legacy-to-new capability mapping

| Legacy capability | New owning module | Migration treatment |
| --- | --- | --- |
| File chunk upload, upload inspection and merge | Uploads | Replace with MinIO multipart sessions and presigned part URLs; remove local chunk files and synchronous merge |
| Uploaded-data CRUD and satellite-data CRUD | Assets | Merge into logical assets, immutable versions and typed extensions |
| Geo envelope CRUD and intersection query | Assets / vector features | Replace independent envelope records with version footprints and PostGIS spatial search |
| Satellite/sensor tree | Catalogs | Normalize as catalog entities with stable codes and parent relationships |
| Multi-data resource tree | Catalogs | Normalize as hierarchical resource categories |
| Ecological parameter CRUD | Ecology | Preserve as normalized ecological parameters |
| Ecological parameter/resource relationships | Ecology | Replace denormalized names and medium/high code columns with explicit many-to-many mappings |
| Mine satellite task CRUD | Monitoring | Replace with monitoring plans, runs and immutable input snapshots |
| `SendTask` mine task endpoint | Monitoring | Merge into monitoring-plan run creation; remove duplicate entry point |
| Synchronous Excel exports | None in first version | Exclude; retain a future Export Job extension point only |

### 3. Technology baseline

- Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2 and GeoAlchemy2.
- Synchronous PostgreSQL access for API and workers, with session scope explicit at request or task boundary.
- Alembic owns all PostgreSQL/PostGIS schema changes.
- PostgreSQL with PostGIS is the only relational and spatial database.
- MinIO owns immutable binary objects and generated artifacts.
- RabbitMQ is the Celery broker; PostgreSQL Job records are authoritative.
- Celery runs ingestion, raster/vector processing, retries and asynchronous cleanup.
- A dedicated Scheduler evaluates intervals and RRULEs; dynamic business schedules are not stored in Celery Beat.
- TiTiler serves COG tiles and remains internal behind a signed tile gateway.
- Rasterio/GDAL, Shapely, PyProj and NumPy form the base geospatial worker stack. Additional scientific libraries are added by algorithm-specific dependency groups only.
- `uv` manages Python and dependency groups; Ruff and Pyright enforce code quality.
- Docker Compose is the first deployment target. Nginx fronts API and tile traffic.
- Prometheus collects metrics; Grafana is an optional development profile.

### 4. Runtime and module boundaries

- The repository is a modular monolith. API, Dispatcher, Scheduler and Worker share domain code but have separate process entry points.
- The API image excludes GDAL and scientific dependencies. The Geo Worker image contains native geospatial dependencies.
- Modules are vertical business slices: core, assets, uploads, catalogs, ecology, jobs, processing, monitoring, vector features and tiles.
- Routers perform HTTP adaptation only. Services own use cases and transactions. Repositories own persistence queries.
- Business modules do not query another module's tables directly. Cross-module use cases call the owning module's service or an explicit application interface.
- External systems are accessed through small adapters so MinIO, Celery/TiTiler and clock behavior can be substituted in integration tests.

### 5. Core persistence decisions

- All core entity identifiers use UUIDv7 stored as PostgreSQL `uuid`.
- All persisted timestamps are UTC and all API timestamps include an offset.
- Asset storage is split into logical asset, immutable asset version, typed version extension and artifact.
- Raster, vector and attachment are physical types. Source and business category are metadata, not separate asset tables.
- `object_blob` records content hash, immutable object key, size and reference count. Logical assets may share one blob.
- Raster COG remains in the source CRS. Footprints and API spatial inputs use EPSG:4326.
- Vector files remain in MinIO and features are imported into a common PostGIS feature store with JSONB properties and spatial indexes organized by asset/version.
- Frequently filtered STAC-aligned fields are typed columns. Optional business metadata uses JSONB validated by a referenced JSON Schema.
- Monitoring runs reference concrete asset versions through a relationship table; comma-separated identifiers are prohibited.
- `owner_id` and `created_by` are nullable UUID fields in the first version. They have no user-table foreign key until authentication is introduced.

### 6. API contracts

- All endpoints use the `/api/v1` prefix.
- Resource success responses are direct JSON representations, not a global `{code, message, data}` envelope.
- List endpoints return `items`, `total`, `page` and `page_size`.
- Errors use RFC 9457 `application/problem+json` with a stable application `code` and `trace_id` extension.
- Request validation, domain conflict, missing resource and infrastructure failure map to distinct HTTP statuses.
- Spatial request bodies use GeoJSON Polygon or MultiPolygon in EPSG:4326.
- Complex asset search may use a dedicated search resource rather than encoding large geometries in query parameters.
- Job progress is polled in the first version. Job events retain enough information for a future SSE adapter.
- File downloads use short-lived signed URLs. TiTiler is never exposed directly; raster tile templates use short-lived asset/version-scoped tokens.
- Full STAC API compatibility is deferred, but asset fields and search semantics remain compatible with future STAC projection.

### 7. Asset and Job state decisions

Asset-version processing distinguishes at least upload in progress, validating, processing, needs input, ready, failed and deleted states. Transitions occur through explicit services rather than arbitrary model updates.

Job processing distinguishes at least pending, queued, running, retrying, needs input, succeeded, failed, cancel requested, cancelled and missed states. Terminal state changes append a Job event.

- Job and Outbox rows are created in the same PostgreSQL transaction.
- Dispatcher delivery is at least once. Worker handlers and artifact creation are idempotent by Job and processing-step key.
- Transient dependency failures retry with exponential backoff and bounded attempts.
- Deterministic validation and data errors fail or enter `NEEDS_INPUT` without automatic retry.
- User-supplied CRS or render metadata resumes the existing Job from the blocked step.
- Soft deletion hides assets immediately. A seven-day retention window precedes asynchronous physical cleanup.
- Blob cleanup occurs only when no live asset version references the content-addressed object.

### 8. Monitoring-plan decisions

- A monitoring plan contains boundary, ecological constraints, resource constraints, schedule, active period and scheduling state.
- Supported schedules are fixed intervals and RFC 5545 RRULE. Both are normalized to a persisted next-run time.
- Scheduler singleton behavior on PostgreSQL uses a database lock so duplicate scheduler processes cannot create the same occurrence.
- After downtime, only the most recent missed occurrence is created; older occurrences are recorded as missed.
- Each run searches for ready asset versions created or acquired after the previous successful run and matching spatial and catalog/ecological constraints.
- The selected asset-version set becomes immutable before processing begins.
- The first version creates selection and run records but does not implement repository-absent remote-sensing algorithms.

### 9. Stage plan

#### Stage 0 — Legacy inventory and acceptance baseline

**Objective:** turn the Java repository into a complete migration reference before Python implementation begins.

**Work packages:**

- Catalogue every business Controller method in the multidata and geo modules.
- Record request fields, filters, response meaning, database tables, side effects and cross-module dependencies.
- Classify every method as migrate, merge, replace or exclude.
- Document known defects that must not be reproduced: malformed route, duplicate task creation, comma-separated IDs, synchronous file processing, local paths and custom delimited responses.
- Select small legal test fixtures: one multiband GeoTIFF, one single-band GeoTIFF, one missing-CRS raster, one GeoJSON, one packaged Shapefile, one GeoPackage and one ordinary attachment.
- Write the manual acceptance script before implementation starts.

**Exit criteria:**

- Every legacy business method appears exactly once in the use-case matrix.
- All first-version business capabilities have a target module and acceptance scenario.
- Test fixtures and expected observable outcomes are recorded.
- There is no unresolved dependency on a RuoYi-only module.

#### Stage 1 — New repository and executable foundation

**Objective:** create a runnable, observable skeleton with stable engineering conventions.

**Work packages:**

- Initialize Python 3.12 and `uv` dependency groups for API, Geo Worker, development and tests.
- Configure Ruff, Pyright and Pytest.
- Build API and Geo Worker images separately.
- Create Compose services for Nginx, API, PostgreSQL/PostGIS, MinIO, RabbitMQ, TiTiler, Dispatcher, Scheduler, Worker and Prometheus; keep Grafana optional.
- Add typed configuration, secret injection, structured JSON logging, trace identifiers and health/readiness endpoints.
- Establish SQLAlchemy session boundaries, GeoAlchemy types, Alembic conventions and UUIDv7 generation.
- Implement RFC 9457 exception mapping and standard pagination primitives.
- Add the first migration enabling required PostgreSQL extensions.

**Exit criteria:**

- A clean machine can start the stack from documented commands.
- API, PostgreSQL, MinIO, RabbitMQ and TiTiler readiness checks pass.
- Alembic upgrade and downgrade smoke checks pass against a disposable database.
- API and Worker images demonstrate separate dependency sets.
- One request produces correlated structured logs and baseline Prometheus metrics.

#### Stage 2 — Raster vertical slice

**Objective:** prove the highest-risk end-to-end path before broad CRUD migration.

**Work packages:**

- Implement logical asset, asset version, raster extension, artifact, object blob, upload session, Job, Job event and Outbox models.
- Implement MinIO multipart session creation, presigned part URLs, completion and abort.
- Commit asset version, processing Job and Outbox atomically after upload completion.
- Implement Dispatcher claim, publish, acknowledgment and stale-claim recovery.
- Implement idempotent raster-ingestion task steps: validate, hash, deduplicate, inspect metadata, create COG, calculate statistics, create thumbnail, calculate EPSG:4326 footprint and publish artifacts.
- Implement `NEEDS_INPUT` diagnostics and resume for missing CRS or ambiguous rendering metadata.
- Implement asset/version detail, Job polling, artifact detail, raster render profile and spatial search APIs.
- Implement internal TiTiler access and short-lived signed tile templates through Nginx.

**Exit criteria:**

- A multiband GeoTIFF completes the manual flow from upload to map tile display.
- A single-band raster receives a usable default grayscale profile.
- A missing-CRS raster enters `NEEDS_INPUT`, resumes after metadata submission and becomes ready without re-upload.
- Replaying the same task does not create duplicate artifacts.
- Uploading identical bytes creates distinct logical records when requested but reuses one blob.
- A failed RabbitMQ publication is eventually delivered from Outbox without losing the Job.

#### Stage 3 — Vector and attachment coverage

**Objective:** complete the three first-version physical asset types on the shared asset lifecycle.

**Work packages:**

- Add vector and attachment version extensions.
- Detect and validate GeoJSON, packaged Shapefile and GeoPackage inputs.
- Retain source vector objects in MinIO and import features to PostGIS with normalized CRS and JSONB properties.
- Add feature count, geometry type, property schema, extent and import diagnostics.
- Add feature-level bounding-box/intersection search with pagination.
- Add ordinary attachment validation and signed download.
- Add JSON Schema registration and validation for type-specific or business-specific properties.
- Complete asset version creation and version-history APIs.

**Exit criteria:**

- GeoJSON, Shapefile and GeoPackage fixtures import with expected feature counts and extents.
- Feature intersection search returns only matching asset-version features.
- An invalid vector archive fails with an actionable diagnostic and does not leave partial live features.
- An ordinary attachment reaches ready state without invoking geospatial processing.
- A second version does not mutate a Job or monitoring snapshot that references the first version.

#### Stage 4 — Business catalogs and ecological mappings

**Objective:** migrate the normalized business-reference capabilities required by asset search and monitoring.

**Work packages:**

- Implement hierarchical resource categories with stable codes and parent relationships.
- Implement satellite and sensor entities and their hierarchy/relationships.
- Implement ecological parameters.
- Implement explicit many-to-many ecological-parameter/resource mappings.
- Connect asset metadata to resource category, satellite and sensor references.
- Replace legacy tree DTOs with documented business tree resources.
- Convert any useful repository reference values into explicit, idempotent seed operations.

**Exit criteria:**

- Catalog trees can be created, updated, reordered and queried without RuoYi menu/tree classes.
- Duplicate codes and invalid parent cycles are rejected consistently.
- Asset search filters correctly by category, satellite, sensor and ecological mapping.
- No denormalized display name is used as a relationship key.

#### Stage 5 — Monitoring plans and scheduling

**Objective:** replace mine satellite tasks and duplicate send-task behavior with an executable monitoring domain.

**Work packages:**

- Implement monitoring plan, recurrence, occurrence, run and run-input snapshot models.
- Implement fixed-interval and RRULE validation and next-run calculation.
- Implement the Scheduler with PostgreSQL locking and deterministic occurrence identity.
- Generate Job and Outbox records for due occurrences.
- Implement incremental selection since the previous successful run using boundary intersection, readiness, category and ecological constraints.
- Freeze selected asset versions before the run advances.
- Implement missed-occurrence behavior and plan activation/deactivation.
- Expose plan, run, input snapshot and manual-trigger APIs.

**Exit criteria:**

- A plan produces one and only one run at its due time.
- Restart after several missed periods creates only the latest run and records older occurrences as missed.
- A second run selects only newly eligible asset versions.
- Editing an asset after snapshot creation does not change the recorded run inputs.
- The legacy mine-task and send-task use cases are both covered by the new plan/run workflow.

#### Stage 6 — Lifecycle, resilience and operational hardening

**Objective:** make the complete first-version system safe to operate with large local datasets.

**Work packages:**

- Implement soft deletion, restore within seven days, expiration and asynchronous cleanup.
- Implement blob reference accounting and retryable MinIO cleanup.
- Add bounded task timeouts, retry policies, cancellation checkpoints and per-task temporary directories.
- Configure Geo Worker concurrency conservatively, beginning at two processes.
- Add disk-space preflight checks and cleanup for temporary files.
- Add metrics for request latency, errors, Outbox backlog, RabbitMQ queue depth, Job duration/failure, Worker utilization and storage usage.
- Add database indexes and query plans for asset search, footprints, vector features, Job claiming and scheduler due-time queries.
- Run representative 2–100 GB operational rehearsals where hardware permits; otherwise document extrapolated limits from smaller fixtures.

**Exit criteria:**

- Deleted assets disappear from normal search, restore during retention and clean safely after expiration.
- Shared blobs are not deleted while referenced by any live version.
- Worker failure and restart do not corrupt Job state or duplicate artifacts.
- Temporary storage exhaustion fails early with a clear diagnostic.
- Operational dashboards expose queue backlog, failures and processing duration.
- The documented single-host concurrency does not destabilize PostgreSQL or MinIO.

#### Stage 7 — Migration closure and release candidate

**Objective:** prove first-version scope completeness and hand the new repository to frontend integration.

**Work packages:**

- Reconcile the final implementation with the Stage 0 use-case matrix.
- Execute the complete manual end-to-end acceptance script on a clean Compose environment.
- Run critical integration tests and focused state/spatial/scheduling tests.
- Review OpenAPI for stable naming, pagination and RFC 9457 behavior.
- Produce developer startup, migration, backup/restore, troubleshooting and test-fixture documentation.
- Record known limits for single-host storage, Worker concurrency and unsupported formats.
- Confirm no runtime dependency on RuoYi, MySQL, local upload paths or Java services.

**Exit criteria:**

- Every included legacy business use case is demonstrably handled by the new system.
- All excluded methods have an explicit scope reason.
- The full clean-environment acceptance run passes.
- The frontend can integrate using only OpenAPI and the documented tile/upload workflows.
- The release candidate can be rebuilt from source and migrations without manual database edits.

### 10. Delivery gates and sequencing

- Stages 0 and 1 are mandatory prerequisites for Stage 2.
- Stage 2 is the architectural gate. Broad CRUD migration must not hide a broken raster vertical slice.
- Stage 3 depends on the asset, upload and Job lifecycle established in Stage 2.
- Stage 4 can begin after the stable asset foreign-key interfaces from Stage 2, but must complete before Stage 5 acceptance.
- Stage 5 depends on ready-asset search, spatial footprint queries and catalog/ecological filters.
- Stage 6 begins incrementally but cannot be declared complete until Stages 2–5 are functionally complete.
- Stage 7 is the only point at which the first-version migration is considered complete.

Recommended delivery units are small vertical work items that end in an observable API or worker behavior. Database-only, repository-only and router-only tasks should be avoided unless they are prerequisites inside the same delivery unit.

### 11. Definition of Done for a work item

A work item is done only when:

- Its user-visible or operator-visible behavior is accessible through the highest applicable seam.
- Schema changes are represented by Alembic and work on a clean database.
- Errors follow RFC 9457 and include a trace identifier.
- Retries or duplicate requests have a documented idempotency outcome.
- Relevant structured logs and metrics exist.
- The manual acceptance step is documented and executed.
- High-risk infrastructure behavior has an integration test where practical.
- The use-case matrix and OpenAPI/documentation are updated in the same change.
- `README.md` stage board (status, current work, delivered capabilities) is updated in the same change whenever a stage starts, lands, or closes.

## Testing Decisions

### Testing philosophy

- Manual end-to-end testing is the primary acceptance mechanism because the migration's main risk lies in interactions among MinIO multipart upload, PostgreSQL/PostGIS, Outbox, RabbitMQ/Celery, GDAL processing and TiTiler.
- Tests assert externally observable behavior and persisted business state, not internal method calls or framework implementation details.
- The highest practical test seam is preferred. For ingestion, the preferred seam begins with upload-session creation and ends with a ready asset, artifacts and retrievable tile. For monitoring, it begins with a due plan and ends with a run and immutable input snapshot.
- Integration tests cover infrastructure boundaries that are costly or unreliable to verify manually on every change.
- Do not add process-in unit tests for state machines, CRUD, Pydantic mapping, ORM getters, thin wrappers or framework defaults.

### Primary manual end-to-end seams

1. Raster happy path: multipart upload → completion → Outbox → Celery → COG/thumbnail/footprint → ready asset → signed tile display.
2. Raster correction path: missing CRS → `NEEDS_INPUT` → metadata submission → resume → ready asset.
3. Duplicate-content path: upload identical bytes twice → distinct requested logical records → one shared blob.
4. Vector path: upload packaged vector → import features → spatial search → signed original download.
5. Attachment path: upload ordinary file → ready state → signed download without geospatial processing.
6. Version path: create a second version → old Job snapshot remains bound to the first version.
7. Monitoring path: due plan → incremental spatial/catalog/ecological selection → immutable run snapshot.
8. Recovery path: broker unavailable during creation → Outbox backlog → broker recovery → exactly one effective Job execution.
9. Deletion path: soft delete → hidden search result → restore; then repeat and allow seven-day cleanup using an accelerated test clock.
10. Restart path: scheduler downtime across multiple occurrences → only latest occurrence runs → older ones marked missed.

### Integration-test seams

- Alembic migrations against real PostgreSQL/PostGIS.
- Geometry storage, CRS normalization and spatial index queries.
- MinIO multipart initiation, completion, abort, signed download and object cleanup.
- RabbitMQ/Celery dispatch, redelivery and transient retry behavior.
- Outbox concurrent claiming, successful acknowledgment and stale-claim recovery.
- TiTiler reading private COG objects and tile-gateway token validation.
- Scheduler lock, occurrence uniqueness and missed-run recovery.
- Vector import transaction behavior and partial-import cleanup.

### Test fixtures and repeatability

- Geospatial fixtures remain deliberately small enough for routine local execution while retaining real CRS, band and geometry metadata.
- Large-file behavior is rehearsed separately and does not block the routine suite.
- Manual acceptance steps use stable identifiers and expected counts rather than visual judgment alone.
- Tests control time where retention, recurrence or retry delays are involved.
- Infrastructure tests run against disposable services and never assume developer machine state.

## Out of Scope

The following are explicitly outside this first-version migration specification:

- RuoYi users, roles, permissions, menus, departments, posts and data scopes.
- Login, registration, captcha, password reset and JWT issuance.
- RuoYi dictionaries, system configuration, notices, operation logs, login logs, online users, server monitoring and cache administration.
- Quartz, code generator, Druid administration and RuoYi framework compatibility.
- Compatibility with legacy URL paths, response envelopes or frontend code.
- MySQL production-data migration; no production business data exists.
- Excel or CSV export implementation.
- Full STAC API implementation.
- SSE or WebSocket Job notifications.
- Remote-sensing algorithms not present in the legacy repository.
- Microservices, Kubernetes, Kafka, Redis Broker, Airflow, Prefect, Temporal, Dask and Spark.
- Public or remote deployment of the unauthenticated first version.
- GPU processing and algorithm-specific ML runtimes.
- Multi-node high availability in the first deployment.

## Further Notes

- The first version is local-development only. PostgreSQL, RabbitMQ, MinIO and TiTiler must not be exposed as public services.
- A 100 GB source may require 200–300 GB of temporary working space depending on GDAL operations. Disk capacity and I/O contention are release constraints, not merely deployment tuning.
- Geo Worker concurrency starts at two on the single host and is increased only after observing memory, temporary-disk and MinIO/PostgreSQL I/O behavior.
- The old repository's embedded SQL contains table definitions and mapper statements rather than production data. Any reference seed values discovered later must be reviewed as business data before inclusion.
- The existing repository does not provide Issue Tracker configuration or a `ready-for-agent` label vocabulary. This specification is therefore published as a project document rather than an external issue.
- The next specification after Stage 7 should cover authentication and authorization: PostgreSQL users, Argon2, JWT access token, `ADMIN/USER`, shared-read/owner-write enforcement, administrator-only account management and protected tile/download token issuance.
