### 2.3 关键关系事实

1. **两个对接项目是一对，不是两个独立系统**。openpitmines 是业务主体（用户、矿山、任务编排、业务落库），eco-fastapi 是它通过 `application.yml` 的 `thirdparty` 配置调用的算法引擎（`http://localhost:18080`，见 `ruoyi-admin/src/main/resources/application.yml` 的 `inversion-service` / `preprocess-service` 段）；eco-fastapi 的 Worker 反过来通过 `JavaApiClient` 回调 Java 侧（登录与部分落库）。
2. **共用数据库**。两者读写同一套 PostGIS 表（`backend_satellite_data`、`backend_uav_data`、`backend_ecological_parameter_result`、`backend_inversion_job` 等）：Java 侧登记元数据，Python 侧回写 COG 转换状态与空间覆盖。
3. **上传与计算分离**。文件上传（分片/秒传/合并）全部在 Java 侧 `/backend/minio`；Python 侧只以 `bucket + object` 引用已上传文件（"引用式"契约），计算成果再写回 MinIO。
4. **瓦片服务能力同源**。eco-fastapi 内嵌 TiTiler（用 `?minio_bucket=&minio_object=` 替代官方 `?url=`）+ Redis 缓存；openpitmines 另有 Map3DServer（:7000）做渲染、GeoServer 发布 WMS。本仓库 tiles 模块同样是 TiTiler + HMAC 受控访问。

## 3. 基准：旧系统接口覆盖（55 端点 / 10 领域）

通用约定：`AjaxResult = {code:int, msg:string, data?:T}`；`TableDataInfo = {total:long, rows:T[], code:int, msg:string}`；列表接口通用查询参数 `pageNum:int, pageSize:int`（PageHelper 分页）。接口数与行为已与 `doc/旧接口迁移矩阵.md` 逐项核对一致。

## 5. 对接项目一：eco-remote-sensing-fastapi

### 5.1 定位与技术栈

生态遥感监测计算后端（矿山场景：卫星/无人机/外业数据 → 生态参量反演 → 退化诊断 → 开采跟踪）。FastAPI API + Celery Worker 双运行面，DDD/Ports-and-Adapters 架构。**API 是轻量接入面**：只做请求校验、用例调用、Celery 任务投递、任务状态查询和地图瓦片服务，计算全部在 Worker。

- Python 3.10（strict）、FastAPI 0.118.x、Pydantic v2、SQLAlchemy 2.0 async + asyncpg、geoalchemy2（PostGIS）
- Celery 5.6（RabbitMQ broker）、Redis（结果后端 + 瓦片缓存）
- MinIO（无 S3 SDK，经 GDAL `/vsis3/` 或 HTTP URL 直读）、rasterio、rio-tiler、titiler 0.18（TilerFactory 内嵌）、morecantile、shapely、pyproj
- 无全局 URL 前缀、**无任何鉴权**（CORS `*`）；响应统一 `ResponseModel{data, status, message, error_code, description}`，下述"出参"均指 data 字段内容
- 上游是 Java 主后端（openpitmines，8088）：Java → 本服务投递任务；本服务 Worker → `/internal/*` 回写 + JavaApiClient 回调 Java

### 5.2 接口规模

自研业务接口 49 条路由（48 个操作）；TiTiler 工厂约 28 条路径；合计约 77 条。**能力缺口**：无分片上传/秒传/合并接口（上传由 Java 侧完成，本服务仅引用 bucket+object）；无数据资源目录/树形目录 API；无数据导出/下载 API。

### 7.2 关键语义差异

| 差异点 | 旧系统 | 新平台 | eco-fastapi | openpitmines |
|---|---|---|---|---|
| 主键 | Long 自增 | UUIDv7 | satellite_id:str 等混合 | 自增/字符串混合 |
| 空间范围表示 | mapExtent 拼接串 `minX@!@minY@!@maxX@!@maxY` | footprint Geometry(POLYGON,4326) + bbox 四列 | spatial_coverage:Geometry（GeoJSON 写入） | spatial_coverage:Geometry（入参为 GeoJSON 串） |
| 关联方式 | 逗号分隔 ID 串 | 关联表 / UUID 外键 | JSONB 数组（ecological_ids） | JSON 数组（sub_task、ecological_ids） |
| 资产语义 | 文件即记录，可覆盖修改 | 逻辑资产 + 不可变版本 + 成果分离 | 成果表直接覆盖更新（file_status 流转） | 主表 + 临时表覆盖式合并 |
| 时间语义 | Date 无时区 | UTC 持久化 + API 带时区 | date/datetime 混合 | yyyy-MM-dd 串 |
| 任务语义 | 同步计算，cycle 字段伪调度 | Job 状态机 + Outbox + 监测计划调度（RRULE） | Celery 任务 + Redis 快照轮询 | 转发 Celery + STOMP WebSocket 推送 |
| 响应协议 | AjaxResult/TableDataInfo | REST + RFC 9457 + {items,total,page,page_size} | ResponseModel{data,...} | R{code,msg,data} |
| 鉴权 | 若依 JWT（部分无注解） | JWT + 受控下载/瓦片 | 无 | JWT（上传模块匿名放行） |

## 8. 初步对接建议（事实性梳理，不构成方案）

### 8.1 候选对接面

1. **数据供给**：新平台 assets 的 COG/THUMBNAIL 成果 + 签名下载 URL + tiles 令牌，可供监管系统消费。对方为"引用式"契约（bucket+object），既可按对象键对接，也可按签名 URL 对接；需注意对方读取路径是 `http://{endpoint}/{bucket}/{object}` 直读与 `/vsis3/`，与本项目"MinIO 不直接暴露、经短期签名访问"的边界约束存在拓扑差异。
2. **计算委托**：新平台 Job/monitoring 可委托 eco-fastapi 的任务接口（`/preprocess/*`、`/inverse/task`、`/diagnosis/task/*`）。对方契约以 mine_id 为业务锚点、Celery task_id 为异步句柄、Redis 快照轮询进度，与本项目 Job 轮询模型（poll_hint）可对接，但需建立 job_id ↔ celery task_id 映射。
3. **成果回流**：eco-fastapi 的 `/internal/*` 回写通道与 Worker 侧 JavaApiClient 模式提示了成果回写路径。若本项目委托计算，需设计成果登记（asset_artifact + asset_version 引用），而非直连对方数据库。
4. **瓦片互认**：本项目 tiles（TiTiler + HMAC）与 eco-fastapi TiTiler（minio_bucket/minio_object + Redis 缓存 + rescale/色带约定）能力同源，语义上可互认，但访问控制模型不同（HMAC 令牌 vs 匿名直读）。

### 8.2 主要差距与风险

- **身份锚点不同**：新平台以 asset/asset_version 为中心；对方以 mine_id + 数据类型表（satellite/uav/ecological）为中心。跨系统引用需要显式映射层。
- **生态参数编码体系需统一**：旧 ecoparamCode、对方 ecological_category（"0101" 等）、新平台 ecological_parameter.code 三套编码需建立对照表。
- **鉴权与网络边界**：eco-fastapi 完全无鉴权、openpitmines 上传模块匿名放行；本项目有 JWT 与受控访问约束。对接必须经网关/内网隔离，不得绕过本项目的下载与瓦片访问边界（总体架构约束）。
- **部署拓扑**：当前各系统均为本机开发端口（8088/18080/7000/8080），Map3DServer 甚至指向特定内网 IP（10.206.0.10），对接时需先明确部署边界。
- **双库事务与覆盖语义**：openpitmines 的成果覆盖式合并（临时表→主表，业务键冲突替换）与本项目"版本不可变"不变量冲突，对接时成果应作为新版本/新成果进入，不能复刻覆盖语义。

### 8.3 后续动作建议

1. 确定对接形态（数据供给 / 计算委托 / 双向）后，为对接接口单独做契约设计，建议以 `/api/v1` 下新增对外资源的方式暴露，而非暴露内部实现。
2. 建立三套生态参数编码与两套产品类型编号（旧 dataResourceCode、对方 product_type 000114 等）的对照表。
3. 若委托计算，设计 Job ↔ 外部任务 ID 映射、进度轮询接缝与确定性/瞬时错误分类的映射（对方 Celery 状态 → 本项目 Job 状态机）。
